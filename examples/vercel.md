## 1-pager

### Ship agent-written frontend changes to production with a preview-gated check

**Problem.** Startup engineering teams building edge-first apps with AI coding tools can generate frontend changes quickly, but there is no clear check that an agent-written change is safe before it reaches production. Vercel says deploys should not break anything (e8). The pain itself is unvalidated and is the first thing to test (r5).

**What we propose.** A preview-gated release check that runs on the preview deployment of an agent-written change, shows what changed, and only then lets the team promote it to production. It aims to give fast AI-assisted building a safer path to live release, in line with Vercel's stated goal that deploying should not break anything (e8, e1).

**For.** Startup engineering teams shipping edge-first apps with AI coding tools (e24, r1)

**Key points**

- Startups building edge-first from the start are a named Vercel customer segment (e24).
- Developers using AI coding tools report saving 30-60% of coding, testing, and documentation time (e11), so more code is produced faster.
- AI coding tool use is rising, with developer usage of Claude and Cursor up sharply year over year (e12).
- Vercel states that deploying should not break anything and that teams should create code without fear (e8).
- The pain point is a hypothesis; the first step is interviews to test it before any build (r5).

**Proof points**

- e24: Vercel names startups building edge-first from the start as customers.
- e8: Vercel says deploying should not break anything in a large team.
- e11: Developers using AI coding tools report saving 30-60% of time on coding, testing, and documentation.
- e12: Developer usage of Claude and Cursor has risen sharply year over year.

**Next step.** Let's run interviews with startup engineering leads on Vercel using AI coding tools to test whether unverified agent-written changes are a real release risk before we decide whether to prototype.

## MVP idea

_A proposal of what to build. Nothing has been built._

- **Goal:** Let a startup team check an agent-written frontend change on its preview deployment and promote it to production only after it passes a visible review step.
- **Target user:** Startup engineering teams shipping edge-first apps with AI coding tools (e24, r1)
- **Core job:** Unverified AI-written frontend changes reaching production

**Must-have features**

- **Preview change summary:** Shows what an agent-written change touches on its preview deployment, so the team can see it before release. Tests the pain named in r5 and the deploy-safety claim in e8. `r5, e8`
- **Promotion gate:** Blocks promotion from preview to production until the team has reviewed the summary and approved it. This is the core safety step for the job. `e8, r3`
- **Agent workflow tagging:** Records which change came from an AI coding tool, so the team and the test can see which agent workflows are actually run. Needed to validate r5's question. `r5, e12`
- **Release history log:** Keeps a record of each gated promotion, giving test teams a concrete view of release activity over time. `e8`

**Out of scope**

- Pricing, billing, plan changes, or usage-credit features (r6 and r7 not tested here)
- Team seat management and enterprise features such as SSO, SCIM, or managed WAF (r11)
- Non-Next.js framework support or infrastructure-control features, which the pack does not document
- Cloudflare or Netlify comparison features or migration tools
- Marketing campaigns, Series D outreach, or sales motion (r14, r16)

**Success criteria**

- Interviewed startup teams confirm, before build, that unverified agent-written changes are a real release risk (action a1 result)
- Test teams complete at least one preview-to-production promotion through the gate on a real project
- Test teams can say, in their own words, what the change summary showed that they could not see before
- Results are recorded as test findings, not as proven demand

**How a user tries it.** A startup engineer uses an AI coding tool to change a page on an edge-first web app. The change is pushed and creates a preview deployment. Instead of going straight to production, the preview shows a short summary of what the agent changed, tagged as agent-written. The engineer reviews the summary, sees the change touches only the intended page, and approves the promotion. The release is recorded in the history log. The demo shows the gate, the summary, and the log, without any billing or team-management screens.
